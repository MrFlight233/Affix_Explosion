# 模板缓存与 DB 同步修复

> 日期：2026-07-27  
> 状态：已实现

## 1. 背景与根因

模板相关接口（`GET /api/data/*`、`GET /api/admin/*`）**只读内存缓存**。  
Admin 写操作原先是「写 SQL + `setAffix/setEntity(请求合并对象)`」，导致：

- SQL 漏列时，缓存里有完整字段，DB 没有
- 界面当次进程「保存成功」，重启后丢失

## 2. 漏列清单

| 表 | 漏写列 | 影响 |
|----|--------|------|
| affixes | `targeting_modifier`、`has_passive_bonuses` | Targeting 覆写 / 被动开关不落库；create 的 filled 还会直接丢掉这两字段 |
| entities | `target_condition` | 实体条件 Targeting 不落库 |
| categories | （无） | 字段与 SQL 已对齐 |

## 3. 实现要点

### 3.1 SQL 补列

- `affixRepo` INSERT/UPDATE 写入 `targeting_modifier`、`has_passive_bonuses`
- `entityRepo` INSERT/UPDATE 写入 `target_condition`
- create 的 filled 合并对象包含上述字段

### 3.2 写后回读

create/update 成功后：

```ts
SELECT * FROM affixes/entities WHERE id = ?
→ affixRowToDef / entityRowToDef
→ templateCache.setXxx(persisted)
```

保证 **缓存 ≡ 当前 DB 行**。若将来再漏列，Admin 会立刻看不到该字段（暴露漏写）。

### 3.3 清除语义

- Admin：覆写关闭 / 无条件 Targeting → 传 `null`（避免 `JSON.stringify` 丢掉 key）
- Repo：`patch.xxx === null` → merged 中清除为 `undefined`，写入 DB 为 null

## 4. 设计预留标注

文档示例词条**不补种子、不补库**（由用户手动添加）。已在 design 标明：

- `has_debuff` / `most_buffs` / 「弱点感知」：**预留**（战斗未维护 `_activeDebuffs` / `_activeBuffs`）
- 「治疗引导」：索敌可改友方；真正治疗还需武器 `damage < 0`

## 5. 验收清单

1. 词条设 Targeting 覆写 → 查库 `targeting_modifier` 非空 → 重启后仍在
2. 关覆写 → 库为 null → 重启仍无
3. 新建带覆写词条 → 查库 + 重启仍在
4. `hasPassiveBonuses` → 库为 1 → 重启一致
5. 实体 `targetCondition` → 非空 / 清空为 null → 重启一致
6. （可选）战斗挂 `sortBy: hp_asc` 词条，索敌与日志符合预期

## 6. 明确不做

- 种子 / 库补充示例 targeting 词条
- 实现 buff/debuff 战斗状态机
- 改战斗引擎索敌逻辑、schema/迁移（列已存在）
