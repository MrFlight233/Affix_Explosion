# 战斗引擎：从可变步长改为固定时间步长

## Context

当前战斗引擎使用「下一事件时间推进」模式：每轮扫描所有武器找最小的 `remainingTime` 作为 `dt`，直接跳到下一把武器触发的时刻。这导致：

- 恢复（HP/耐力）以不均匀的大块方式应用（dt 可能从几百到几千毫秒）
- 时间不是"正常走"的 — 引擎跳着走，只在武器即将触发时才推进
- 用户期望的是一个正常的、均匀推进的时间线：每固定间隔检查一次状态，该触发的就触发

## 目标

将 `_runBattleCore` 改为**固定时间步长**（50ms/tick），时间均匀推进，每个 tick 内检查所有武器是否到达触发时刻。

## 变更范围

仅修改 **1 个文件**：`project/client/src/game/engine.ts` 中的 `_runBattleCore` 方法。

`runCombat` 和 `runSimCombat` 无需改动（它们只是传参调用 `_runBattleCore`）。UI 层（`sim-battle.ts` / `panels.ts`）无需改动 — 已通过 `onEvent` 回调和独立的 rAF 轮询与引擎解耦。

## 当前架构

### 引擎核心循环 `_runBattleCore`（engine.ts:766-892）

```
while (双方都有存活单位 && simTime < 120000) {
  1. 扫描所有武器，找最小 remainingTime → dt
  2. 等待 max(dt / speed, 50) ms 真实时间
  3. simTime += dt
  4. 所有单位：恢复 HP/耐力（按 dt 比例）、武器 remainingTime -= dt
  5. 触发所有 remainingTime ≤ 0 的武器
  6. 更新 combatPlayerUnits / combatEnemyUnits 供 UI 轮询
}
```

### 武器运行时结构

```typescript
interface CombatWeaponRuntime {
  name: string;
  actionTime: number;      // 冷却间隔（ms），如 2000
  remainingTime: number;   // 剩余冷却时间（ms），初始 = actionTime
  damage: number;
  staminaCost: number;
  targetType: string;
  targetOrder: string;
  priorityTarget: number | null;
  targetFaction: string;
}
```

### speed 参数

- `runCombat`（正式战斗）：传 `number`，恒定速度
- `runSimCombat`（模拟战斗）：传 `() => state.combatSpeed` getter 函数，支持运行时变速

引擎内统一处理：`const currentSpeed = typeof speed === 'function' ? speed() : speed;`

### UI 与引擎的关系

UI 通过两个独立通道获取战斗数据：

1. **`onEvent` 回调**（即时推送）：每次武器触发时，引擎调用 `onEvent({ time, actorName, damage, targetHpAfter, ... })`，UI 即时追加战斗日志
2. **`combatPlayerUnits` / `combatEnemyUnits` 轮询**（50ms rAF）：`patchBattleValues()` 每 50ms 读取引擎上的运行时单位，更新 HP/耐力/CD 显示。CD 使用插值：`displayMs = rawRemaining - wallElapsed * combatSpeed`

## 具体变更

### `_runBattleCore` 改造

**删除：** 可变 dt 计算逻辑（当前第 788-807 行）

```typescript
// 删除这一段：
let dt = Infinity;
const allWeapons: { ... }[] = [];
for (const u of playerUnits) {
  if (u.currentHp <= 0) continue;
  for (const w of u.weapons) {
    if (w.remainingTime < dt) dt = w.remainingTime;  // 找最小值
    allWeapons.push({ unit: u, weapon: w, isPlayer: true });
  }
}
for (const e of enemyUnits) { ... }
if (dt === Infinity || dt <= 0) dt = 100; // fallback
```

**替换为：** 固定步长 + 独立构建武器列表

```typescript
const TICK_MS = 50; // 固定时间步长：50ms（20 ticks/秒）

// 构建武器列表（不再同时找最小 remainingTime）
const allWeapons: { unit: CombatUnitRuntime; weapon: CombatWeaponRuntime; isPlayer: boolean }[] = [];
for (const u of playerUnits) {
  if (u.currentHp <= 0) continue;
  for (const w of u.weapons) {
    allWeapons.push({ unit: u, weapon: w, isPlayer: true });
  }
}
for (const e of enemyUnits) {
  if (e.currentHp <= 0) continue;
  for (const w of e.weapons) {
    allWeapons.push({ unit: e, weapon: w, isPlayer: false });
  }
}
```

**修改：** 等待时间

```typescript
// 旧：await delay(Math.max(dt / currentSpeed, 50));
// 新：
await delay(Math.max(TICK_MS / currentSpeed, 50));
```

**修改：** 时间推进

```typescript
// 旧：simTime += dt;
// 新：
simTime += TICK_MS;
```

**修改：** 恢复和冷却递减（4 处 `dt` → `TICK_MS`）

```typescript
// 旧：u.currentStamina + u.staminaRegen * dt / 1000
// 新：u.currentStamina + u.staminaRegen * TICK_MS / 1000

// 旧：w.remainingTime -= dt;
// 新：w.remainingTime -= TICK_MS;
```

**保持不变：** 武器触发循环、目标选择、事件发射、击杀检测 — 完全不变。

### 改造后的完整循环

```
while (双方都有存活单位 && simTime < 120000) {
  1. 构建 allWeapons 列表
  2. 等待 max(TICK_MS / speed, 50) ms
  3. simTime += TICK_MS
  4. 所有单位：恢复 HP/耐力（按 TICK_MS 比例）、remainingTime -= TICK_MS
  5. 触发所有 remainingTime ≤ 0 的武器（可能多把）
  6. 更新 combatPlayerUnits / combatEnemyUnits
}
```

## 影响分析

| 方面 | 可变 dt（旧） | 固定 50ms（新） |
|------|-------------|----------------|
| 武器触发精度 | 精确到 ms（dt=remainingTime 精确跳转） | ±50ms 误差（tick 对齐） |
| 恢复粒度 | 不均匀大块（dt 从几十到几千 ms） | 均匀 50ms 小块，更平滑 |
| 每 tick 触发武器数 | 通常 1 把 | 可能多把同时触发 |
| CPU 开销 | 低（跳过大段空闲） | 略高（20 tick/秒 × speed） |
| 时间线理解 | 跳跃式，不直观 | 均匀推进，直观 |
| 同一 tick 多武器触发顺序 | 几乎不会发生 | 按 allWeapons 迭代顺序（玩家→敌人，同一方按单位的武器列表顺序） |

50ms 的触发误差在文字游戏中完全可接受。speed=1 时每秒 20 tick，speed=4 时每秒 80 tick，开销可控。

## 关于并行武器触发

当前可变 dt 模式下，dt 精确跳到最近武器的触发时刻，所以几乎不会有两个武器在同一 tick 触发（除非它们的 actionTime 完全相同）。

改为固定 50ms 后，可能在同一个 tick 内同时触发多把武器（例如剑 cd 2000ms 和弓 cd 3000ms 都可能在 tick 40 = 2000ms 时触发，如果弓也恰好对齐）。

引擎现有的 `for (const { unit, weapon, isPlayer } of allWeapons)` 循环已经能正确处理这种情况 — 迭代顺序是玩家单位在前、敌方在后，同一方的武器按原始列表顺序。在一个 tick 内，先触发的武器可能直接击杀目标，后面的武器通过 `if (target.currentHp <= 0)` 的 `selectTarget` 内部的 `alive` 过滤自然跳过已死亡的敌人。行为是合理且确定的。

## 不需要修改的部分

1. **`runCombat`** / **`runSimCombat`**：只传参，不改
2. **`buildCombatRuntime`**：初始化 `remainingTime = actionTime`，不改
3. **`selectTarget`**：目标选择逻辑，不改
4. **`onEvent` 回调**：事件格式，不改
5. **UI 层 `sim-battle.ts`**：`onEvent` 即时日志 + `patchBattleValues` 轮询 + CD 插值，全部不变
6. **UI 层 `panels.ts`**：正式战斗 UI，不变

## 验证步骤

1. `npx tsc --noEmit`（client 目录）— 编译零错误
2. 模拟战斗 — 选择双方 BD，开始战斗：
   - 战斗日志中武器触发时间是否合理（不再跳大段时间）
   - HP/耐力恢复是否平滑
   - 同一 tick 多武器触发是否正常
3. 变速测试 — 切换 1×/2×/4× 速度，验证战斗正常
4. 暂停/继续 — 验证暂停期间时间停止、数值不变
5. 正式战斗（`runCombat`）— 走一遍完整流程
