# AI 计划方案编写

受众是**其它智能体**：文档必须具体到文件路径、改动要点与可勾选验收，不是给人读的散文设计稿。

完整骨架见 [templates.md](templates.md)；优质样例与反例见 [examples.md](examples.md)。

## 硬性规则

1. **先询问，后执行**：范围未确认前只写/改计划文档，不直接改业务代码（用户明确要求立刻实现除外）。
2. **计划落 `doc/`**：新建 `doc/YYYY-MM-DD-<主题简述>.md`；修改计划时更新同一文档，或标为「已被取代」并链到新文档。
3. **机制变更同步 `design/`**：改动游戏规则/名词/战斗等机制时，同步更新 `design/` 对应文档，并在计划中列出链接。
4. **语言**：简体中文。
5. **不批量改写**历史 `doc/` 旧文件名；新文档一律用日期前缀命名。

## 工作流

1. 向用户确认目标、范围、不做项（1–2 个关键问题即可）。
2. 按任务选**一类**模板，勿混用：
   - **Bug 修复** → 问题 / 根因 / 修复 / 验收
   - **功能·交互·小重构** → 目标 / 选型或根因 / 实现要点 / 验收 / design
   - **大型机制·框架** → 定位 / 协议与规则 / 文件表 / 分阶段 / 验证 / 影响
3. 写入或更新 `doc/YYYY-MM-DD-*.md`，文首元信息填日期与状态。
4. 若改游戏机制 → 同步 `design/`，并在计划「相关设计文档」列出。
5. 写完跑一遍下方**可执行性自检**；状态保持 `计划中` 直至实现完成再改为 `已实现`。

## 文首元信息

```markdown
# <标题>

> 日期：YYYY-MM-DD  
> 状态：计划中 | 已实现 | 部分实现 | 已被取代  
> （可选）取代：… / 见 `[新文档](./…)` / 与 `design/…` 同步
```

状态流转：`计划中` → `已实现` / `部分实现` → `已被取代`（取代时必须链到新文档）。

## 三类精简模板

### A. Bug 修复

- 问题描述（现象、复现）
- 根因分析（可按可能性排序；定位到文件+机制）
- 修复方案（按文件：路径 + 改什么；关键处给片段）
- 验收清单（可勾选）
- 明确不做（可选）

### B. 功能 / 交互 / 小重构

- 目标（一句话 + 约束）
- 选型或根因（表格对比结论，或错误行为表）
- 实现要点（按文件/模块分节，含路径）
- 验收用例（可勾选）
- 相关设计文档（有机制变更时必填）

### C. 大型机制 / 框架

- Context / 定位（解决什么、不介入什么）
- 核心抽象与数据协议（规则、类型、数据流）
- 涉及文件与改动表（路径级）
- 实施顺序（Phase / Step）
- 验证方式
- 影响分析 / 明确不做 / 扩展预留（按需）

## 可执行性自检

写完必须全部满足：

- [ ] 标题与文件名能看出主题；路径为 `doc/YYYY-MM-DD-*.md`
- [ ] 文首有日期与状态；若取代旧方案则双向可追溯
- [ ] 每个改动点有**真实仓库路径**（如 `project/client/src/...`）
- [ ] 实现要点足以让另一智能体不猜意图即可动手（必要处有代码片段）
- [ ] 验收条目可观察、可判定通过/失败
- [ ] 「明确不做」或变更范围写清，避免扩大施工
- [ ] 机制变更已列 `design/` 同步项（或明确无需同步及原因）

## 反例（禁止）

- 只有概述，无文件路径
- 验收写成「测试一下」「应该没问题」
- 改了实现思路却不更新 `doc/`
- 改了槽位/战斗/词条等机制却不同步 `design/`
- 把 design 全文塞进计划，或用计划替代 design

## 与 CLAUDE.md 的关系

本 Skill 落实「计划入 doc + 机制改 design」。`design/` 描述游戏机制真相；`doc/` 描述某次可执行施工方案。
